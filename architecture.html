Architecture · ai-testing-academy

AI Testing Academy — how the whole thing is put together

A single-page React site that teaches QA automation and runs three AI-backed tools (resume review, mock interview, question-bank enrichment) entirely from the browser. There is no backend of its own: the user brings an API key, or an optional shared proxy in the monorepo answers for them. This page walks the runtime shape, the provider abstraction, the content model, and where to extend each one.

1 · What it is

One page: a launcher, then six numbered sections stacked in reading order. Three are static teaching content; three call a language model. Everything below exists to serve that split.

static ⚙️ Connection Setup Pick a provider and model, paste a key or lean on the server default, and test the round trip before anything else runs.
AI · JSON 📄 Resume & CV Agent Parses an uploaded PDF/DOCX in-browser, scores it as structured JSON, rewrites it, and exports the result back to PDF.
static 🎓 Lecture Series Course tracks and lecture links. Content lives in the component itself, not the locale files.
AI · chat 🎙️ Mock Interview A five-stage interviewer driven by one long system prompt, ending in a scored verdict on a sentinel token.
AI · grounded ❓ Interview Questions A curated bank, plus a “enrich with fresh questions” action that runs a web-grounded Gemini call.
static 🐍 Coding Challenges 40 Python problems across three levels — each a prompt, then a hint, then a solution with complexity.

2 · Runtime shape

The build output is static files. At runtime the browser is the whole application: it holds the key, it formats the request, it talks to the model vendor directly. The optional /api hop exists only so first-time visitors get a working demo without owning a key.

The two transports

default path Bring your own key The key stays in localStorage and is attached to a fetch() made from the page itself. Anthropic requires anthropic-dangerous-direct-browser-access for this to be allowed at all — that header is what makes browser-origin calls legal, and it is set deliberately.
fallback path Shared server proxy On mount the app probes GET /api/ai/config. If it reports Gemini as available and the user has not opted into their own key, calls route through POST /api/ai/generate instead, and no key ever reaches the client. A failed or missing probe simply returns {} — the site then insists on a user key rather than breaking.
Why the dev proxy exists. Vite's SPA fallback answers /api/* with index.html at HTTP 200, so res.ok passes and res.json() chokes on HTML — the site would silently conclude no server key exists and grey out the panel. vite.config.ts therefore proxies /api to the sibling api-server package (API_PORT, default 8787) in development. In production one origin serves both, so the relative path just works.

3 · Composition

App.tsx is a provider stack and nothing else. Each layer is there for a reason, and the order matters in exactly one place: ProviderContextProvider reads translated error strings, so it has to sit inside LocaleProvider.

ErrorBoundary — Outermost, because the failure it catches is a whole-page failure. Several things below throw on purpose — every useX must be used within XProvider guard, and the decks' manifest parser — and without something to land in, each of them took the document to blank white.
TooltipProvider — Radix tooltip root for the shadcn/ui primitives.
LocaleProvider — Resolves the language once, exposes locale / S, stamps lang and dir on <html>.
AuthProvider — Google sign-in. Inside LocaleProvider because Google renders the button's own label and has to be handed the current language.
ProgressProvider — Per-tool progress, so the launcher can offer to continue where the reader stopped.
ProviderContextProvider — Owns provider/model/key state and the callClaude / callGrounded functions every AI feature uses.
WouterRouter — Base path taken from import.meta.env.BASE_URL, so the app works under a sub-path deploy.
Switch → HomePage | NotFound — One real route. The router is here for the sub-path handling and the 404, not for navigation.

Below the router

HomePage owns two pieces of page-level chrome — the theme and the nav drawer — and then renders the sections. Everything else a section needs, it pulls from context itself. That is the reason the page component stays under 100 lines while the sections it renders are hundreds.

One list decides the order. lib/sections.ts exports SECTIONS — id and number, in reading order — and both HomePage and Nav render from it. There used to be three answers to “what order are the sections in”: the array in locale.nav.links, the JSX here, and the static prerender in index.html. None of them agreed, so reading down the nav jumped the visitor 16237 → 1144 → 13693 → 2749 → 3648 → 4597 pixels, the scroll-spy highlight travelled 2 → 4 → 5 → 6 → 3 → 1 as you scrolled, and the numbered headings counted 01 → 03 → 02 with three sections carrying no number at all. The numbers are stored rather than derived from the array index, because they appear on screen: changing the order should be a visible decision about renumbering, not a silent one.
The shape to notice. No component imports a vendor SDK, a URL, or a key. They import useProviderContext() and call a function. Swapping a vendor, adding a proxy, or changing a header touches lib/providers.ts alone.

4 · The AI layer

lib/providers.ts is the only file that knows any vendor exists. PROVIDERS is a registry of strategy objects — one per vendor — behind a uniform interface, so the call site never branches on which one is selected.

Three exported entry points

callAI()
The general path. Chooses proxy vs direct, validates the key, builds, sends, and parses — returning a plain string.
callGeminiGrounded()
Adds the google_search tool so answers cite live sources. Used only by the question-bank enrichment.
extractJSON()
Pulls a JSON object or array out of a model reply — strips a ```json fence, scans for the first balanced value (string-aware, so trailing citations don’t leak in), and repairs a near-miss reply with jsonrepair (missing or trailing commas, unescaped quotes, a truncated tail) before parsing. This is what makes “return only JSON” prompts survive a chatty, imperfect model.

Failure handling is part of the contract

  • A thrown fetch (CORS, offline, blocked host) is translated into an explanatory message naming the host that was refused — not a bare TypeError.
  • A non-2xx response carries the status plus the first 300 characters of the body, so the user sees the vendor's own complaint.
  • A wrong-shaped key is rejected before any request is made, via validateKey — pasting an sk-ant- key into the OpenAI slot fails locally.
  • Every error string comes from the active locale, so the failure path is translated as carefully as the happy path.

5 · Content & i18n

en.ts is the source of truth for structure; he.ts is declared as const he: Locale where Locale = typeof en. That single annotation means the compiler rejects a Hebrew file that drops a key, misspells one, or falls behind a new section. Translation drift is a build error, not a runtime blank.

resolution order Which language wins ?lang= query param → localStorage.ata_lang → navigator.language starting with he → en. The result is written back to storage, so a link with ?lang=he is sticky.
direction RTL is data, not a branch Each locale carries its own dir. applyHtmlAttrs() stamps lang and dir onto <html> and CSS logical properties do the rest — no component checks the language.
switching Full reload, on purpose switchLang() writes the choice and reloads with the new query param. A reload guarantees direction, fonts and third-party widgets all re-lay out cleanly, which a re-render does not.
prompts Prompts live in the locale The resume, rewrite and interview system prompts sit under locale.prompts, so tuning model behaviour is a content edit — and each language can steer the model in its own words.
Where a string lives depends on how much of it there is. Short copy sits in lib/locales/{en,he}.ts. Bodies of content large enough to drown a locale file get their own module — lib/questionBank.ts and lib/lectures.ts — exporting an EN/HE pair with the same compiler-checked shape. The lecture catalogue lived inside components/LectureSeries.tsx until it did not: 336 of that file's 425 lines were the two data objects, which made editing a blurb an edit to a component and left the catalogue with no importer other than the thing that rendered it. Moving it out is also what lets the prerender generator read it, since a build script cannot import from a component.

One shape in the nav is worth calling out: locale.nav.labels is keyed by section id, not ordered. The order is lib/sections.ts; only the words are translated.

The challenge content model

lib/challenges.ts declares types only — no data. The UI depends on the shape, and the shape is currently satisfied by the locale files; an API or CMS could satisfy it later without touching a component.

6 · Feature modules

📄 Resume Agent — the heavyweight

At ~575 lines it is the largest component, because it is really a small document pipeline: read a file, extract text, score it, rewrite it, export it. All of it client-side.

extract

pdf.js or mammoth turns an uploaded PDF/DOCX into plain text in the browser.

→
score

callClaude() with the resume prompt, then extractJSON() into scores, strengths, gaps.

→
rewrite

A second call with the improve prompt returns ATS-friendly prose, not JSON.

→
export

lib/resumePdf.ts builds the PDF with jsPDF, embedding a Hebrew face for RTL.

All four libraries are bundled dependencies, reached through dynamic import() so they are fetched on first use rather than on page load. Nothing is pulled from a public CDN: the runtime-injection loader that used to walk cdnjs → jsDelivr → unpkg is gone, along with the exposure it carried. The cost has moved from CDN reachability to size — pdf.js and its worker are about 1.6 MB, and fetching them is the slowest part of the first upload by a wide margin.

The export must be text, not a picture. An applicant tracking system reads the text layer, so a résumé rendered as an image fails the first automated sift while looking perfect to the person holding it. That is why the Hebrew path embeds a font and reorders each line into visual order rather than rasterising, and why pdfFromCanvas() survives only as the fallback for when the font itself cannot be fetched.

The same principle runs in reverse on the way in. extractPdf() counts the text runs pdf.js finds, and a file with none is reported as what it is — a scan, or a résumé exported as an image — rather than as a generic extraction failure, because the reader whose only copy is a picture has a problem well beyond this upload. Reading also reports progress: the zone names the wait for the parser itself, then counts pages as it goes, so a large file never leaves one unchanging line on screen. The file input is cleared after every pick, since a picker holding the same file fires no change event and the obvious retry would otherwise do nothing at all.

🔐 Sign in with Google

AuthProvider plus a GoogleSignIn control in the nav drawer. Google's hosted client is loaded on demand, draws its own button, and hands back an ID token; lib/googleIdentity.ts reads the name, address and picture out of it and nothing else. Google renders the button's label itself, so the current language is passed to renderButton — that half of the translation cannot come from a strings file.

In the browser it is identity, not authorisation. The token is read here and never verified: checking a signature needs Google's keys and a server trusted to use them, and the page has neither. Anyone can hand it a hand-written token and appear signed in as anybody, so nothing on the client is gated on it — the profile is good for a name and an avatar in the corner and for nothing else.

On the server it is verified, and that is where decisions are made. The condition this page used to state — “if any of that arrives, the token has to go to api-server and come back verified first” — is what now happens. When the token is sent to api-server as a bearer credential, lib/googleAuth.ts checks the signature against Google's published keys and then the issuer, audience, expiry and email_verified before any claim in it counts. The algorithm is pinned to RS256 rather than read out of the token, which is how alg: none and key-confusion attacks get in. That is what GET /api/entitlements/course answers from.

The two halves are not in tension: reading a token for display and verifying one for a decision are different jobs, and only the second needs a server. A Pages build still has no server, so it still has no entitlements — it renders the profile and nothing more.

A build with no VITE_GOOGLE_CLIENT_ID renders no sign-in at all and never contacts Google, so a deployment that has not been given an OAuth client stays whole rather than showing a button that cannot work.

🎙️ Interview Agent

A rolling Message[] is kept in a ref and resent whole on every turn — the model holds the conversation, the client holds no session. The five-stage structure lives entirely in locale.prompts.interview. Ending the interview sends the sentinel ___VERDICT___, which the prompt binds to “stop and produce a scored verdict”.

❓ Question Bank

Five collapsed stages, each holding questions that are themselves the control: one click reveals a hint, a second reveals the full answer, a third collapses. That is QuestionCard over the same useDisclosure(3) the coding challenges use, so both sections of the site behave identically and neither owns stage logic.

Content — 75 questions per language (fifteen per stage, 150 in all), each with a hint and a multi-paragraph answer — lives in lib/questionBank.ts rather than in the component, which would otherwise be mostly prose. The section renders whatever the bank contains and never counts stages or items.

The enrich action feeds the user's role and a fixed keyword seed into callGrounded(), then extractJSON() lifts a questions array out of the reply. Grounding is why this one path is Gemini-only.

🐍 Coding Challenges

The section maps levels to ChallengeCards and knows nothing else. Each card owns its own useDisclosure(3) — prompt → hint → solution → collapsed — so the list never tracks a stage per index and adding challenges cannot regress the reveal logic.

7 · State & persistence

There is no store. State is React state in two contexts plus local component state, and the only thing that survives a reload is what is deliberately written under the ata_ prefix — to localStorage when it should outlive the visit, to sessionStorage when it should not.

Storage is input, not state. Every read goes through lib/storage.ts, for two reasons that apply to all eleven keys. Storage can be unavailable — private browsing, blocked cookies, a full quota — and getItem throws rather than returning null when it is, which in a module-scope initialiser takes the page down before it renders. And the contents are editable from any devtools console, so a value read back has to be validated like anything else that arrives from outside. Every failure is the same answer: the value is absent, and the caller's default applies.

resetSettings() deliberately does not sweep the whole prefix. It removes the provider selection, the per-vendor keys and their remember flags, and nothing else: resetting which model you talk to should not also erase your progress, your interview history, your résumé drafts, or which account you are signed in as.

Why the transcript and the drafts are session-scoped. Both hold what someone wrote about their own career, on a machine that may not be theirs. The résumé drafts were always sessionStorage; the interview transcript was localStorage and permanent, which was the same class of content on the opposite lifetime for no stated reason. It is a session now, which is exactly as long as “resume after a reload” needs. Transcripts left behind by the old version are deleted rather than migrated — carrying one into the session would carry the problem forward a visit.

The key-mode decision

One subtlety worth naming: ownKeyTouched. Until the user explicitly toggles the switch, the app re-derives the mode whenever the provider changes or the server config arrives — a stored key or the absence of a server default turns own-key mode on. Once the user touches it, their choice is respected and never recomputed.

The flag is held in a ref as well as in state, because the effect has to read it without re-running on it: the effect exists to re-evaluate the default when the provider changes or the config lands, and firing it because someone just flipped the toggle would undo the flip. That is a dependency the effect genuinely must not have, which is worth saying in a ref rather than in a suppression comment.

hooks/useReveal Scroll-in animation One IntersectionObserver per section adds .in and then unobserves, so each element animates exactly once and the observer disconnects on unmount.
Nav Scroll-spy A second observer with a -25% / -65% root margin highlights whichever section is in the reading band, not merely on screen.
HomePage Drawer without a flash The nav-ready class lands after a double requestAnimationFrame, so CSS transitions are only enabled after the first paint and the drawer cannot animate on load.
Nav Drawer that is really closed Below 900px the sidebar is moved off-screen by a transform, which hides it from eyes and from nobody else: it kept visibility: visible and all twelve of its controls stayed in the tab order, so keyboard focus vanished for twelve stops before reaching the page. inert takes the subtree out of focus and out of the accessibility tree in one inherited attribute.
ScrollProgress One write per frame The bar's width is written straight to the element inside a requestAnimationFrame rather than held in React state — a scroll handler that calls setState re-renders on every event of a long page to move one CSS property.
lib/domUtils Safe rendering of model text esc(), linkifyHtml() and findLinks() escape first and only then insert <strong>/<a> — markdown from a model is rendered without handing it an HTML injection.

Accessibility affordances already in place

  • A skip link to #main-content, translated like everything else.
  • aria-expanded on every disclosure button, and aria-label on the icon-only nav and language toggles.
  • Theme is an attribute on <html> (data-theme), so CSS — not JS — resolves colour, and the first paint is already correct. That last clause is newly true: the attribute used to be written in an effect after React mounted, and because this page's own app ships a static prerender, first contentful paint put finished content on screen in the light palette and the whole page then flipped.
  • Both lang and dir are set on the document element, which is what screen readers and the bidi algorithm actually read.
  • The mobile drawer behaves as the modal it looks like: inert while closed, Escape to dismiss, focus moved to the first link on open and returned to the toggle on close, and an aria-label that follows aria-expanded instead of announcing “Open navigation menu, expanded”.
Focus return is keyed off the transition, not off where focus is. The obvious implementation asks whether document.activeElement is <body> and puts focus back if so. It silently never fires: by the time the effect runs React has already applied inert, and the browser blurs whatever was inside the subtree when it does, so there is nothing left to recognise. Tracking the open → closed edge is what actually observes the event, and it also stops a drawer that was never opened from claiming focus on mount.

9 · Trust boundaries

Be explicit about the key. In own-key mode the API key lives in localStorage and is sent from the page to the vendor. That is the accepted trade for a backend-free teaching site — any script running on this origin could read it, and the key is exposed to the browser's network log. The proxy path exists precisely so a casual visitor never has to make that trade.
  • Untrusted input is model output. Everything a model returns is escaped before it reaches the DOM; the markdown renderer builds its tags from parsed groups, never by interpolating raw text.
  • No secret is bundled. Server-side keys stay in api-server; the client only ever learns the boolean available and a default model name.
  • Error bodies are truncated to 300 characters before display, which keeps a verbose upstream error from dumping a wall of text into the UI.
  • One third-party script, by necessity. Google's sign-in client is loaded from accounts.google.com and runs on this origin — there is no packaged equivalent, the credential flow only exists inside the hosted client. It is the only runtime code on the site that does not ship with it, it is requested only when an OAuth client is configured, and the résumé libraries that used to be fetched from public CDNs are now bundled dependencies.
  • Sign-in proves nothing in the browser. The ID token is read here, not verified, so identity on the client is a display convenience and not a security claim — nothing on the page is gated on it, because treating it as authorisation would mean trusting a value any visitor can forge.
  • It proves something once the server has checked it. Sent to api-server as a bearer credential, the same token is verified against Google's published keys — signature, issuer, audience, expiry, email_verified — and only then does a claim in it decide anything. That is the whole difference between the two halves, and it is why the entitlement answer lives on the server and not in the bundle.
  • A purchase record is never written by a browser. Rows in course_purchases come from a signature-verified Stripe webhook and from nowhere else. The googleSubject a row carries is stamped into the checkout session from a token the server verified, so it is not a field any client can set — the checkout schema is strict and rejects the attempt.
  • The seed route is an admin route. POST /api/stripe/seed writes a product and a price to a live Stripe account. It requires ADMIN_API_TOKEN as a bearer token, compared in constant time over hashes so a length mismatch cannot leak through an exception, and answers 404 rather than 401 when no token is configured — an unconfigured deployment should not advertise that the surface exists, and forgetting the variable should fail closed.
The client ID is not a secret. VITE_GOOGLE_CLIENT_ID is inlined into the bundle by design and is readable by anyone who opens it; committing it changes nothing about who can see it, and Google enforces which origins may use it. A client secret is a different thing entirely and must never become a VITE_ variable, because the browser would receive it.

10 · Build & deploy

The package is one workspace inside a pnpm monorepo (artifacts/ai-testing-academy), alongside api-server, portfolio and the lecture sites. Shared dependency versions come from the workspace catalog, which is why so many entries read catalog:.

The prerender is generated because the hand-written one drifted. The block inside #root is what crawlers and social bots read; React replaces it on mount, so no visitor ever sees it and nothing about the page reveals when it goes stale. By the time anyone looked it disagreed with the app in four places — it advertised 10 coding challenges against the app's 40, pointed the first cybersecurity lecture at a dead gamma.app URL, numbered that track from an order that had since changed, and listed hero buttons that had been renamed. Duplicate copy maintained by hand drifts; copy generated from the modules the components render from cannot.

Build-time configuration lives in a committed .env beside the Vite config. Committing it is deliberate and safe for exactly one reason: Vite inlines every VITE_ value into the emitted JavaScript, so nothing there was ever private, and keeping it in the repository is what lets the Pages build produce a working site without a secret store. .env.local is git-ignored and is where anything you would not publish belongs.

The Pages job builds the portfolio at the site root and mounts this site and all ten lecture decks underneath it, copies this page in as architecture.html, and gives each app a 404.html copy of its own shell. The run's Allure report is published separately, to its own reports repository’s Pages, so the test results keep their own URL and never land on the portfolio site.

Why every app gets its own 404, and why the rewrites matter. These are single-page apps: the decks serve /slide1, /slide2, /allslides from one shell and none of those paths is a file. A single root 404.html holding the portfolio meant every unknown path fell back to the portfolio rather than the app that owns it — and for the decks that is not a corner case, because the academy's hreflang tags nominate /ai-testing-lecture-1/slide1?lang=en as a canonical URL. GitHub Pages has no rewrite rules, so the nearest 404.html is the best it can do: the right page, carrying a 404 status. Cloudflare's _redirects rewrites the same paths at 200, which is the reason to prefer it for anything meant to be indexed.
The API image is not the one at the repository root. That one builds the Playwright test image and its CMD runs the suite. server/Dockerfile ships the server, and its runtime stage is unusually thin: build.ts already bundles the whole server — workspace packages, express, drizzle, supabase — with esbuild into a self-contained dist/index.mjs, so the image copies dist/ and nothing else. No node_modules, no pnpm, no source, non-root user. fly.toml deliberately keeps one machine running rather than scaling to zero, because routes/ai.ts builds its rate limiters on an in-memory store with a 24-hour window — a machine that stops and restarts hands every caller a fresh anonymous allowance, and the free-tier quota stops being a quota.
The tooling is TypeScript too. api-server/build.ts (the esbuild driver) and tests/support/start-api-servers.ts (the Playwright webServer entry point) are run straight from source as node ./build.ts. Node strips the types itself from 22.18 on, and CI pins 24, so neither needs a loader, a build step, or a dependency to earn the same typechecking as the rest of the repo — build.ts through its own tsconfig.tools.json, since it sits outside rootDir.

11 · Testing

One Playwright package at tests/ covers six layers — 503 cases at the time of writing (221 unit, 152 component, 49 api, 19 contract, 62 e2e and deck). Playwright is used as the runner throughout, not just as a browser driver: the unit project never launches a browser, it executes the same TypeScript modules the app imports — the academy's, and the server's too, wherever a module has no Express import to drag in.

What decides which layer a test belongs in

One question: what is the cheapest thing that could still be wrong? A rule about a string belongs in a unit test, because a browser adds nothing but seconds. A rule about what a reader can see or reach needs a real one, because that is where the bug lives. The layers below are that question applied, not a taxonomy imposed on top.

principle Assert the acceptance, not only the refusals A verifier that returns “no” to everything passes every rejection test ever written for it, and signs nobody in while looking perfectly secure. So the Google token suite generates an RSA keypair, serves a key set in place of Google's, signs a token, and asserts first that it is accepted. Every rejection after that is the same token with one property changed, so a failure names one rule.
principle A test that cannot fail is worth nothing New tests are checked by mutation — the fix is reverted and the test watched going red. Two cases here were rewritten after they passed against deliberately broken code. One mutation that was not caught is recorded in the source it guards: the token verifier's alg check is defence in depth, because the verify call is already pinned to RSA/sha256, so deleting it changes no outcome.
principle Breadth by reading, depth by running The ten lecture decks are independent artifacts, so the code they share is shared by copy. One unit test reads all ten and asserts they have not drifted apart; one browser test runs a single deck to prove the logic they share actually works. Neither could do the other's job, and together they cost one dev server.
principle No test can reach a vendor, a card or a database The unit suite stubs fetch. The API suite runs servers whose model key is a throwaway that only ever receives invalid requests, whose admin token guards a route that then fails on absent Stripe credentials, and whose DATABASE_URL is blank. A developer's shell cannot change any of it.
LayerRuns inCovers
tests/unit Node domUtils escaping and linkifying, language resolution, the whole provider registry — request building, key validation, error mapping, proxy-vs-direct routing. Also the two things that must hold before a browser is involved: the résumé PDF builders, checked by parsing the emitted file back with pdf.js rather than by asserting which jsPDF calls were made, and the Google ID token reader, checked for reading a Hebrew name intact and for answering “nobody” to every malformed or expired token instead of throwing on page load. Two more since: lib/storage.ts, including the case no real localStorage can be made to produce — one that throws on every call — and the server's token verifier, signing real tokens with a keypair generated in the test process.
tests/component Chromium (Playwright CT + Vite) The real components, mounted: the disclosure cycle, the locale chain, the scroll affordance, the key-mode decisions in ConnectionSetup, the résumé uploader driven with real PDFs through the real pdf.js, sign-in in both languages against a stubbed Google client, and what the interview restores from storage — including that a transcript left in localStorage by an older version is deleted rather than read.
tests/api Node → live server Status codes, CORS, malformed bodies, the webhook signature gate, and the raw-body registration order in app.ts. Also the two authenticated surfaces: the admin token in front of the seed route — including that the right token gets through it, and then fails on Stripe rather than on auth — and the entitlements route, sent tokens shaped exactly like real ones to prove none of them work.
tests/contract Node → live server openapi.yaml ↔ the generated Zod schemas ↔ what the server actually returns, plus the shared customFetch wrapper against real responses.
tests/deck Chromium → a lecture deck One of the ten decks, really running: that the 1920×1080 stage is drawn, that a portrait phone turns it rather than letterboxing it to a fifth of design size, that turning the phone switches the rotation back off, that a tablet is left alone, and that the stage stays 16:9 at every size. One deck is enough because the unit layer proves the other nine carry the same logic.
tests/e2e Chromium, desktop + Pixel 5 The whole app on its own Vite server: hero and section rendering, in-page navigation, the theme and language toggles — including that a tampered stored theme never reaches data-theme — the interview-question reveal, and the mobile nav drawer.

Component and e2e both run twice, at a desktop viewport and as an emulated phone, so a layout that only holds together on a wide window fails here rather than on someone's handset. The one genuinely layout-specific test — the off-canvas drawer — is guarded by the isMobile fixture instead of being duplicated.

Fixtures carry the arrangement, not the specs

tests/component/fixtures.tsx folds “serve the config, then mount inside the providers” into one step per feature, so a spec declares what it wants and never repeats the setup. Two of them are worth naming because they make otherwise untestable things testable.

  • PDFs are built, not stored. tests/support/pdfFixtures.ts assembles an image-only PDF byte by byte — one page, one full-bleed image, no text operators — so the “résumé that is a picture of a résumé” case is exercised without a binary in the repository. Its text-bearing counterpart is produced by the site's own exporter, so fixture and production code cannot drift apart.
  • Google's client is stubbed. The real one renders into a cross-origin iframe and needs an origin registered to the client ID, so the suite serves its own script in place of it. The component's loading path still runs unchanged — it asks for the script, waits for it, and calls the same three methods.
A test that cannot fail is worth nothing. Two cases here were rewritten after they passed against deliberately broken code. setInputFiles raises change whatever the input already holds, so “pick the same file twice” could never reproduce the bug it was written for; the assertion moved to the property that actually makes the retry work — that the picker is left holding nothing. Every regression test in this area is checked by reverting its fix and watching it go red.

The e2e layer uses page objects

Selectors live in classes under tests/e2e/pages and tests/e2e/components, never in a spec. BasePage holds the page handle and the document-level things (the <html> element, the current hash); HomePage adds the section lookups; the nav and hero are component objects because they are fragments reused across flows rather than routes.

One method hides the viewport difference. NavComponent.reveal() opens the drawer when the hamburger is visible and does nothing on desktop, so the same navigation test runs unchanged on both projects. Without it every nav assertion would need a mobile twin.
No test can reach a model vendor — or create a product. The unit suite stubs fetch; the API suite runs one server with a throwaway Gemini key that only ever receives invalid requests, and one with no key at all. All instances start with DATABASE_URL and the Replit connector variables blanked, so a developer's shell cannot make the suite pass or fail by accident — and so the furthest an authorised call to the seed route can get is failing to fetch Stripe credentials.

There are three instances, because most of these routes answer “not configured” before they validate anything. routes/ai.ts answers 503 for a missing key before it reads the body, so on a keyless server the 400 messages is required branch is unreachable; the seed route answers 404 with no admin token, so its 401 branch is unreachable there too. One instance carries nothing, one carries a Gemini key, an admin token and an OAuth client, and a third carries a quota small enough for the rate-limit spec to exhaust. tests/support/start-api-servers.ts builds the server once and starts all three.

Assert the acceptance, not only the refusals. A verifier that returns “no” to everything passes every rejection test ever written for it, and signs nobody in while looking perfectly secure. tests/unit/googleAuth.spec.ts therefore generates an RSA keypair, serves a key set in place of Google's, signs a token, and asserts first that it is accepted — every rejection after that is the same token with one property changed, so each failure is attributable to exactly one rule. The suite was checked by mutation: deleting the audience check turns one case red, and making the verifier return null unconditionally turns five red.

The e2e layer needs no API server at all: it boots the academy's own Vite dev server, whose /api proxy has nothing behind it, so Connection Setup lands in exactly the bring-your-own-key state these flows exercise.

Reports

Every config appends to one allure-results/ at the repo root, so a single Allure report covers the whole run. Locally the configs also emit Playwright blobs, which run-all-tests.sh merges into one HTML report; under CI=true they write HTML directly and the merge is skipped. Screenshots, video and traces are kept on failure and attached to both reports.

The merge has two sharp edges. Each config writes its blob to its own subdirectory — the blob reporter wipes its output directory on start and would otherwise eat the previous layer's archive — and all three archives are named report.zip, so flattening them for merge-reports must rename as it goes or the merge quietly reports a single layer. It also needs -c playwright-merge.config.mts, because the suites record different testDir roots and Playwright will not merge across them.

CI

Typecheck, lint, formatting and every test layer run as their own steps on each push and pull request, and again nightly at 05:00 Israel time. GitHub cron is UTC-only and Israel shifts between UTC+2 and UTC+3, so both candidate hours are scheduled and a gate job discards the one that is not 05:00 locally. Each step carries if: !cancelled(), so one failing layer — or a failing typecheck — never stops the rest from reporting into the shared Allure results. Publishing does not depend on the tests passing. The site job runs through a failed test job and the deploy job asks only whether the site built, because a report nobody can read when the build is red is a report that is missing exactly when it is needed. The Docker image is pinned to linux/amd64 for a related reason: the workspace overrides strip every platform-native optional dependency except the linux-x64-gnu ones, so an arm64 image would be missing the rollup binary and the e2e layer's Vite server would never boot. Both images take the pin, for the same reason.

Lint and formatting are gates now, and that is the whole story of how they drifted. All three checks were defined in package.json and CI ran one of them: the workflow invoked typecheck and the test layers, and the strings lint, eslint, format and prettier did not appear anywhere in it. The result reads exactly as you would predict — typecheck clean, because it was enforced; lint at 32 errors and 590 files off the Prettier config, because they were not. A sweep had in fact already been run once and undone within a day: all 590 files were touched by the 26 commits that landed after it, and none predated it. The fix that holds is the gate, not the sweep.

12 · Extension points

To add…TouchAnd nothing else, because…
A coding challenge or a whole level lib/locales/en.ts + he.ts CodingChallenges maps over whatever the locale provides; it never counts levels or items.
An interview question, or a whole stage lib/questionBank.ts — EN_BANK + HE_BANK Each entry carries its own hint and answer; QuestionBank maps over the stages and QuestionCard owns the reveal. A test asserts every question has both.
A model vendor lib/providers.ts — one ProviderDef The picker renders Object.keys(PROVIDERS) and callAI only ever calls build/parse.
A model to an existing vendor That vendor's models array The dropdown is generated from it; the first entry is the default.
A language A new locale file + the CATALOG map Typing it as Locale makes the compiler enumerate everything still missing.
A page section A component, one entry in lib/sections.ts, one label per locale, and one line in HomePage The nav, the scroll-spy and the section numbering all read SECTIONS, so adding it in one place is what puts it in all three. Re-run pnpm generate-prerender to carry it into the static shell.
A progressive-reveal UI elsewhere useDisclosure(n) It is stage arithmetic only — it has no opinion about what a stage contains.

Where the edges are

  • Lecture content is hardcoded inside LectureSeries.tsx as EN/HE objects rather than living in the locale files — the last section that breaks the content/UI split. The question bank used to do the same and now sits in lib/questionBank.ts; the same move is available here.
  • Grounded search is Gemini-only, so the enrich action degrades if the user is on Anthropic or OpenAI without a Gemini key.
  • The proxy path covers Gemini only. The other two vendors are own-key or nothing.
  • Resume tooling needs the public internet beyond the model call; behind a strict CSP or an offline network, extraction and PDF export are the first things to fail.
  • Nothing calls checkout yet. POST /api/stripe/checkout, the purchase record it produces, and GET /api/entitlements/course are all in place and tested, but no UI in this app starts a purchase — so in practice no row is ever written. The join exists; the flow that would exercise it does not.
  • The purchases table has not been created. It is defined in lib/db/src/schema/coursePurchases.ts and needs one run of pnpm --filter @workspace/db run push against a live DATABASE_URL. Until then the server degrades rather than failing: a completed checkout logs a warning instead of writing, and the entitlement route answers 503.
